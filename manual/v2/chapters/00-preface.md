# 前言

这本书讲的是一件听起来简单、做起来很难的事：**让一笔钱恰好移动一次，并且在任何一步出错之后，都能说清楚它在哪里、应该去哪里、由谁把它送过去。**

LedgerCore 是一个可复现的银行交易实验室。它用 Java 21、Spring Boot 4、PostgreSQL 18 和 React 19 实现了个人转账、企业账户、双人审批的企业付款、500 人规模的工资批次，以及一条经过**独立清算模拟器**的异步付款路径。第二版（V2）在第一版账本内核的基础上，把系统推进到“钱离开银行之后”的世界：结果可能迟到、可能未知、可能被拒绝，回调可能重复、乱序、丢失，进程可能在任何一行代码之后被杀死，数据库可能被恢复到几分钟以前。

## 这本书和别的书有什么不同

第一，**每一个结论都有可以重新执行的证据。** 书中的数字来自仓库里提交过的评分文件；每一段代码摘录都标注了文件路径、行号，并链接到同一个冻结提交（`{{source-sha7}}`）。如果你在自己的机器上按附录 A 重建环境，就能得到同样形状的结果。

第二，**故障是真的。** 本书的崩溃实验不是在单元测试里抛一个异常：被测银行以真实进程运行，在精确的故障点写出检查点文件并阻塞，实验脚本核对进程号与 JAR 哈希之后才杀死它；数据库会话被 `pg_terminate_backend` 真正终止；准备金不足是通过受限的实验命令把模拟准备金真正划走之后发生的。一个从未发生的故障点永远不会被计为“通过”。

第三，**失败与修复都如实呈现。** 第四轮独立审计在上一轮已验收的代码里发现了一个严重缺陷（R4-01：回调已被确认，结算却可能永久丢失）。本书用修复前后两个提交、同一组崩溃窗口的实测结果讲述它，而不是把它改写成一段没有发生过的历史。被否决的索引方案、结论为“不确定”的性能假设，也都按原样保留。

## 读者与预备知识

本书面向有经验的 Java 后端、DevOps、SRE 与平台工程师。你应当熟悉 Spring 的依赖注入与事务、SQL 与索引、HTTP 与 JSON；不需要金融背景——复式记账、应付、准备金、清算这些概念都会在第一次出现时解释清楚，并在附录 C 的术语表中给出中英文对照。

## 如何阅读

每一章大致遵循同一条路径：**业务问题 → 机制图或时序图 → 精确的 Java/SQL/React 实现 → 受控故障 → 观测数据 → 权衡 → 练习与答案。** 章首的深色框写着本章要回答的问题，浅色框列出本章依赖的证据。

图分三类，并在图框左上角标注：

- **机制图**：画的是冻结实现中真实存在的组件、表、状态与转换，不是路线图；
- **实测数据**：数字由生成脚本直接从证据文件读取，缺失即构建失败；
- **真实截图**：来自真实运行的应用与合成数据，标注采集提交。

书中的英文术语第一次出现时给出中文解释；代码、表名、状态值保持原样，便于你在源码中搜索。

## 边界声明

所有资金、人员与机构都是虚构的。LedgerCore 是一个工程实验室，不是经认证的生产银行，也不代表符合新西兰或任何地区的金融监管要求；本书没有进行过渗透测试或监管认证，也不把一个玩具清算模拟器的行为推广为真实银行间结算的保证。书中的性能数字来自一台本地笔记本上的单次或少数几次运行，用来解释机制与权衡，不是容量承诺。
