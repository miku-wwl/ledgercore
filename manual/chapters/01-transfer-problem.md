# 第 1 章　一次转账究竟要解决什么

周五傍晚，Alex 在手机上输入 25.00，点击确认。屏幕转了一会儿，然后显示网络断开。她不知道钱有没有转出去。这个小小的“未知”把软件里的核心问题暴露出来：服务器可能已经提交，响应却没到达浏览器。用户希望再次点击就能查询结果，而不是产生第二笔扣款。

LedgerCore 把这条旅程做成可运行的模拟银行：前端收集意图；会话身份确定客户；Spring MVC 校验请求；转账用例协调账本；PostgreSQL 约束并提交；持久回执供重试查询。每层承担不同职责，最终目标是相同意图只产生一个可确认结果。

![从点击到可恢复结果的路径](manual/figures/01-transfer-flow.svg)

浏览器状态和数据库状态并不共享一次原子操作。数据库可以保证一笔事务全成或全败；TCP 连接不能保证客户端知道服务端已经提交。把“已提交”和“已收到确认”混为一谈，会使网络重试变成重复付款风险。我们把幂等键与回执一起保存，后面第 11 章会拆开讲。

实际界面里，成功结果显示转账完成；响应在提交后被丢弃时，同一标签页重载仍显示待确认意图。Playwright 流程使用 route handler 先让服务端成功完成请求，再主动中断响应，故障是测试注入的真实网络故障，不是模拟一张静态错误图。

![本地运行中的成功回执](manual/assets/screenshots/transfer-success.png)

“可靠”不是页面永远不报错，而是每个可观察状态都能被解释与恢复。该项目只处理本机数据库中的模拟 NZD，没有真实银行通道、支付网络或资金托管。

**停下来想一想。** 如果服务器已提交，但用户点击刷新，哪些数据必须持久化，才能让界面恢复原来的意图？只在 React state 里保存答案够不够？

**可以这样回答：** 不够。浏览器内存会随刷新消失。服务端必须能按客户、操作和幂等键找到请求指纹及成功回执；前端则要保留原始意图与原键，直到可以确定结果。
