# 第 19 章　需求变化如何穿过全栈

设想产品要求“交易历史必须让用户知道资金来自哪里”。这不是只改一个 React 标签。先明确账户视角的业务含义，再查询安全的交易与 Posting 表示，检查服务端是否始终验证账户所有权，定义 OpenAPI 响应类型，更新页面文案，最后补正向、越权和浏览器回归证据。

![同一需求沿 API、数据库、前端与测试贯通](manual/figures/19-cross-stack.svg)

LedgerCore 的历史详情按当前账户视角表达 OUTGOING 或 INCOMING，展示 “This account” 与 “Counterparty”，不返回对方账户 ID。这样的合同同时满足用户识别方向的需要，并缩小不必要的敏感数据暴露。OpenAPI 类型由运行应用生成，减少后端字段与 React 类型分歧。

新字段仍可能带来跨层副作用。备注如果进入幂等指纹，意味着同键、不同备注不再是相同意图；备注如果只保存在浏览器，就不会进入审计事实；若数据库迁移允许旧数据为空，读模型则必须处理兼容形状。需求澄清应先回答业务语义，再决定持久化与 API 结构。

账户 pause、resume 和 close 也是全栈演进的例子：领域服务有生命周期规则，但当前客户 HTTP API 只支持列出、创建、查看，没有把这些转换暴露给用户。不能因为内部方法存在，就把 UI 或教材描述为已经支持该功能。

![真实历史分录详情以 Counterparty 隐藏对方账户 ID](manual/assets/screenshots/history-detail.png)

实现纵向切片后，分别验证迁移、所有权查询、DTO、前端状态、错误文案、自动生成类型与浏览器旅程。API 合同参考 [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.1.html)；合同标准不会替代项目自己的授权测试。

**练习：** 设计“交易备注”。写下用户可见规则、同键请求比较规则、数据库字段约束、历史 API 输出和越权测试，再决定备注属于不可变账务事实还是可编辑元数据。
