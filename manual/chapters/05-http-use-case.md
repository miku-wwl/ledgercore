# 第 5 章　从 HTTP 请求走到用例

用户确认转账后，浏览器向 POST /api/transfers 发送付款账户、收款账户、金额和 Idempotency-Key。认证 Cookie 标识当前会话，CSRF token 证明写请求具备该会话要求的跨站请求保护信息。控制器把认证主体的客户 ID 交给用例；请求体没有“替我选择客户”的字段。

![一次 POST 请求穿过应用边界](manual/figures/05-http-lifecycle.svg)

路由匹配后，Spring Security 先处理认证与 CSRF；Spring MVC 解析 JSON，Bean Validation 和领域解析检查输入。TransferController 再交给 TransferService 执行事务。异常映射器把稳定业务错误转为 RFC 9457 Problem Details，关联 ID 贯穿响应。成功时返回持久回执。

顺序是安全设计的一部分。服务先验证调用者确实拥有源账户，再尝试占用幂等键；防止一个人利用已知键读取他人的回执。所有权检查和余额检查看起来都是 if，但保护的是不同对象：一个保护资源可见性，另一个保护经济约束。

接口契约把 JSON 金额规定为两位小数的字符串而非浮点数，把未认证、CSRF、余额不足和权限隐藏映射成不同状态。跨客户账户用统一 404，减少资源存在性泄露。客户端只处理合同中可见的安全消息，不应把 Java 异常细节直接显示出来。

服务器处理成功而响应丢失的时点位于用例提交之后、浏览器确认之前。HTTP 本身没有给请求添加“只执行一次”的魔法；应用协议必须提供稳定意图键。我们将在第 11 章追踪数据库如何持久化它。

**检查理解：** 客户 ID 应从哪里取得？为什么不能信任请求体？如果 CSRF token 有效，但 session principal 不是账户所有者，请求是否应通过？答案分别是服务端认证主体、不可被客户端伪造的身份上下文、以及仍然必须拒绝。
