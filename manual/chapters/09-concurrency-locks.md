# 第 9 章　并发转账、行锁与死锁

Alice 从账户 A 转到 B，Bob 同时从 B 转回 A。若两个事务都先锁自己付款账户，T1 等待 B，T2 等待 A，等待图形成环，这就是经典死锁。数据库可以检测并终止其中一个事务，但对用户来说，一笔本可成功的转账会收到重试错误。

![锁顺序打破双向转账死锁环](manual/figures/10-lock-order.svg)

PostgreSQL [显式锁文档](https://www.postgresql.org/docs/18/explicit-locking.html)说明行级锁等待与死锁；LedgerCore 将两个账本账户 ID 去重并按 UUID 自然序排序，然后逐行 SELECT FOR UPDATE。双向转账因此都以同一顺序取得行锁，形成一致的等待方向。锁住 ledger_accounts 而非仅锁余额投影，是因为账本行是目标账户生命周期与写入顺序共同使用的协调点。

行锁持有到事务提交或回滚。付款校验、Posting 写入和投影重建都处在锁保护范围。缩短事务有助于减少排队：不要在取得资金行锁后等待外部 HTTP 服务，也不要把无关报表计算塞进同一转账事务。

排序降低由资源顺序相反引起的死锁，但不证明系统永远无死锁：触发器、外键和未来新增写入路径都可能改变等待图。所有资金写路径都必须遵循相同的全序；数据库仍需保留死锁检测和明确的重试策略。

并发不变量可写成数量关系：初始付款余额为 100，两个独立转出请求各 80。无论调度如何，最多一个成功，失败者应因可用余额不足而拒绝；提交后的付款余额非负，成功收款方增加 80。测试应分别观察 HTTP/业务结果与数据库事实。

![两个付款意图争夺同一有限余额](manual/figures/09-concurrent-transfers.svg)

如果两笔转账的金额分别为 70 和 40，成功结果仍不能超过 100。谁先取得行锁决定哪一笔检查到足够余额，系统不承诺哪位用户更快；它保证的是另一笔会按已提交账本余额被拒绝，而不是让两个陈旧读取都扣款。

**推理练习：** 给出一个锁顺序不一致的例子，并画出等待环。接着给所有资源排序，解释为什么统一的全序能消除这类反向等待，却不能消除未来所有形式的死锁。
