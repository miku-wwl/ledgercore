# 第 20 章　工程取舍、反例与推理方法

可靠性来自一组相互配合的边界，而不是某个“银行级”框架：整数分币避免二进制舍入；复式分录表达守恒；顺序锁与同一事务控制竞争；数据库触发器保护提交状态；幂等回执解决未知结果；服务端授权保护账户；对账暴露投影差异；测试验证跨层协作。

![LedgerCore 的端到端安全属性链](manual/figures/20-end-to-end.svg)

每个选择都有成本。READ COMMITTED 配显式行锁能解释余额竞争，却要求所有写路径尊重同一锁秩序。不可变账本利于追溯，却增加修正和查询成本。余额投影读取简单，却需要同步更新与对账。sessionStorage 可快速恢复同标签页重载，却不能支持跨设备找回。模块化单体让本地事务直接，却限制独立扩缩容。

一个好反例应当能指出被破坏的具体属性。用 double 表示钱会遇到表示误差；先读余额再锁行会允许超额支出；删除旧分录会抹掉历史；超时后换新键可能产生第二笔转账；把账户 ID 隐藏在 UI 中仍可能开放直接 API 访问。随后逐项提出机制并验证它的失效边界。

最值得追问的不是“技术是否先进”，而是：约束在哪里执行？失败后可见状态是什么？两个请求同时到来怎么办？响应丢了怎么恢复？数据来源能否重新核算？测试有没有真正经过冲突边界？结论支持到哪个提交、数据库版本和环境？

LedgerCore 是教育项目和模拟资金系统。它展示金融交易一致性工程中的重要模式，但没有真实银行连接、真实资金、外部审计、生产容量数据或监管认证。把限制写清楚，是工程推理的一部分，不是降低方案价值。

**结课挑战：** 设计一条跨币种转账需求。先列出当前 NZD-only 约束，再说明汇率报价时点、两币种各自的平衡、舍入差额、回滚与幂等指纹需要如何改变。不要直接把币种列改成三字符就宣称支持换汇。
