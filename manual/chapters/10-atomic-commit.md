# 第 10 章　提交、回滚与原子边界

一笔成功转账至少写入三类事实：借贷 Posting、两侧余额投影，以及可供查询的 Transfer 和成功幂等回执。任何一个部分单独提交都会让系统落入难以解释的状态。LedgerCore 用一个 Spring 管理的 READ COMMITTED 事务包住这些操作；PostgreSQL 的 COMMIT 是它们共同可见的边界。

![事务完成之前的写入与失败回滚](manual/figures/10-rollback.svg)

实现先保留幂等意图，锁定账户，检查余额，再写凭证和 Posting，重建投影，插入 Transfer 并封存成功响应。余额不足抛出业务异常时，事务代理回滚；数据库提交触发器在此时校验所有延迟约束。任何 SQL 错误都不能留下“只有扣款、没有收款”的半成品。

Spring 的 @Transactional 只在代理调用与已配置事务管理器边界内有效。若把一部分写入移到异步线程、调用另一个服务进程，或捕获异常后继续返回成功，就不再是原子边界。项目显式选择同进程、同数据库，这让事务保证可以落在一个数据库提交上。

失败有两种不同观察：服务端事务回滚，或客户端无法知道服务器结果。前者在数据库中没有已提交写入；后者需要根据同一幂等键询问已持久化回执。界面不能把超时等同于业务失败。

**自测：** 把一个故障注入到第二条 Posting 插入之后。事务结束时应看到哪些行？应当是没有成功提交的部分状态。测试必须在真实 PostgreSQL 上查询落库结果，Mock 只能证明 Java 调用了预期方法。
