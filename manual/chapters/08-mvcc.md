# 第 8 章　MVCC、快照与可见性

两笔事务同时读取一个值，并不意味着它们在整个过程中看到同一张数据库“照片”。PostgreSQL 18 使用 MVCC 管理行版本；在 READ COMMITTED 下，每一条 SQL 命令都使用当前已提交数据的快照。一个事务的第二条命令可以看到另一事务刚提交的新版本。

![MVCC 下命令快照如何随着提交向前移动](manual/figures/08-mvcc.svg)

转账先锁住付款与收款账本账户行，再通过 Posting 聚合读取权威余额。两个付款尝试争用同一行时，后到者会等待。等待结束后，余额查询作为新的 READ COMMITTED 命令取得新快照，因此不会再用过期的旧余额接受第二笔超额支出。

安全性来自锁、查询与写入的顺序，而不是隔离级别的名字。若先查询余额、后加锁，两笔事务都可能先看见 100.00，再各自计算能够转出 80.00。用显式资源锁把余额检查排在冲突行锁之后，才使这段代码可推理。

锁只覆盖数据库行，应用仍必须用一个事务包住余额检查和 Posting 写入。并发集成测试使用两个独立事务并通过 CountDownLatch 协调起跑；它断言成功转出的合计不会超过开始余额。真实测试避免通过 Thread.sleep 猜测调度时序。

MVCC 也提醒我们，历史分页的两次 HTTP 请求不共享同一快照。稳定的时间与 UUID 游标给出确定排序，但新交易仍可能在用户刷新后出现。不要把“游标稳定”误解成整段浏览期间数据库冻结。

**定位思考：** 为什么在锁之后运行的余额聚合能看见等待期间已经提交的 Posting？如果把锁拆到另一个已提交事务，保护范围会有什么变化？
