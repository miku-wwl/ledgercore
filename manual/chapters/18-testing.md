# 第 18 章　用测试验证边界与故障

测试不是把所有实现都 Mock 掉以后确认调用次数。不同的边界需要不同证据：Money 与 JournalEntry 适合纯单元测试；账户和转账竞争必须在真实 PostgreSQL 上验证锁、触发器、唯一约束与回滚；浏览器流程要经过真实 HTTP 和 Chromium，才能观察 CSRF、Cookie 和刷新后的用户状态。

![从值对象到真实浏览器的证据层级](manual/figures/18-test-pyramid.svg)

转账 PostgreSQL 集成测试覆盖同键并发、余额竞争、双向锁顺序、资金不足、写入失败注入与未知结果回执。完整后端回归有 42 项，包含数据库与模块架构检查。Playwright 一个端到端流程依次注册、开户、余额不足、成功转账、网络响应丢失、重载恢复、分页、跨客户 404、登出、移动视口。

CI 在 main push 时运行 verify 与 dependency-scan。已观察提交 484b9ad 的 Actions run 中两个 job 通过；对应的后续状态文档提交也有绿色远程运行。每一个结论都应标明提交、环境和测试范围，避免把一次成功说成持续保证。

测试之外还要看失败时数据库状态。例如插入第二条 Posting 后故意抛异常，再独立查询确认凭证、两侧余额和回执都没提交。对浏览器未知结果，则必须让服务器成功，再丢弃响应；只模拟 fetch reject 而服务器从未收到请求，测不到最危险的情况。

**测试设计题：** 哪个断言适合放在 Java 单元测试？哪个必须由数据库检查？哪个必须通过浏览器完成？把“借贷平衡构造器”“延迟约束触发器”“用户刷新页面仍用原键”分别匹配。
